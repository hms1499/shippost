# x402 — two settlement models (agent rules)

> Canonical walkthrough: [`docs/ARCHITECTURE.md` §2.3](../../docs/ARCHITECTURE.md) (table + diagram) and the history note there. This file is the short rule set; read §2.3 for the *why*.

The codebase has **two unrelated mechanisms** named "x402" that flow money in **opposite directions**. Do not conflate them.

- **Model 1 — Celo, in-process (we BUY services).** Each pipeline step (`lib/pipeline/*Step.ts`) simulates x402 by pulling stablecoin from **AgentWallet** via `settleX402Call` → cap-enforced `executeX402Call` on Celo. No `X-Payment` header, no HTTP proxy route. The per-thread generate flow uses **only** this.
- **Model 2 — real x402 (we SELL a service).** `app/api/x402/groq/route.ts` via `withX402` (`@x402/next`) + CDP facilitator on Base. The **caller** pays *us* (settles to `X402_PAY_TO`). Does **not** touch AgentWallet. `withX402` verifies the caller's `X-Payment` *before* the handler runs; settle only after a 200 → no payment, no content, no charge. Proven on Base mainnet 2026-06-03 (CDP needs a request-scoped JWT, not a bearer — `lib/x402/server.ts`, `4c48a08`).

**Rule (non-negotiable):** any public, agent-callable x402 surface MUST verify a signed `X-Payment` before any spend, and MUST never expose `settleX402Call` unguarded. This exists because the *original* `/api/x402/*` proxies were an unauthenticated AgentWallet drain (removed in `8f4c222`; safe reintroduction `c8a796b`). Detail: `docs/x402-explained.md`, `docs/x402-flow-diagrams.md`, `docs/x402-mainnet-proof.md`.
